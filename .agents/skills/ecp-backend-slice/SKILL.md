Follow the brief's file ownership; coordinate any needed provider-module, migration, OpenAPI or shared-build scope before touching it. Never substitute a direct foreign-table query/write for a missing API.

## Build in dependency order

1. Implement and test domain roots, value objects, factories and policies from transaction-protected facts. The root owns state transitions and invariants even when called without HTTP. Keep JWT, Spring MVC, JDBC and rows out of domain. Let adapters persist an already valid aggregate; do not leave business status, totals or portion construction to SQL mappers.
2. In each **owning** provider module, implement the required exported `api` contract and its application/adapter path. Export only the facts or operations the consumer needs. Keep that module's writes in its own adapter; every checkout collaborator joins the caller's transaction. Confirm the named interface and allowed dependency, and test locking/ownership at the owner boundary. Do not treat Account ID as SellerShop ID.
3. Implement one consuming input port and handler per use-case intent. Resolve trusted actor/role and ownership in the use case, including direct calls that bypass WebMVC. Commands coordinate roots and collaborators in a transaction, compare replay before mutable inputs, and preserve rollback on any failed collaborator. Queries have separate handlers/read projection ports, enforce owner/visibility in the query, and expose no save method. Their input ports return application-owned immutable views, never types nested in outbound ports. A command may use a narrowly scoped immutable creation snapshot for its response/replay; do not turn the command repository into a general read API.
4. Implement the consuming module's outbound adapters for tables it owns, then WebMVC facade, validation, DTOs, error mapping and adapter-local MapStruct mapping. For paged detail projections, batch related rows for selected IDs; avoid a database call per item or child. Use one SQL statement or a consistent transaction snapshot when mutable state is assembled across statements. Web code depends on an input port, not a concrete handler. Explicit constructors are required; do not use forbidden Lombok constructor/data/builder annotations.
5. Verify the real route and boundaries. Unit tests must exercise the handler wired to HTTP, not a second compile-only or mock-only implementation. Check Modulith/ArchUnit direction **and SQL table ownership**; Java package checks alone cannot detect cross-module SQL. Use PostgreSQL tests for rollback, same-key replay, last-unit, stale-version and other applicable races. Re-run the relevant behavior/contract tests after moving a boundary.

Do not create parallel production command paths to satisfy a RED seam. If tests expose a provisional seam, replace it with the actual input port/handler and move the tests to that path. Do not weaken tests or treat a structural RED as proof of missing business behavior.

Return changed files and reasons, scenario-to-test traceability, actual RED/GREEN results, module and table-ownership checks, unresolved decisions and integration notes. Use `ecp-postgres-change` for SQL/Flyway/locking, `ecp-api-security-contract` for HTTP/security contracts, and `ecp-verify-change` before handoff.

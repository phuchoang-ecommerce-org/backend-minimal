## Design order

1. **Domain model:** Name the owning bounded context, aggregate root, invariants, value objects, factory/policy operations and immutable facts needed by the use case. Separate decisions the domain can make from authentication, orchestration, persistence and presentation. Identify missing domain rules instead of inventing them.
2. **Module collaboration:** For every required fact or mutation, record its owning module and existing exported `api` contract. If an API is missing, specify the smallest immutable fact/query or business operation that the owner must export and which owning adapter implements it. Plan provider API and tests before the consuming handler. Do not plan another module's internal class, repository or table as a dependency. Foreign-table joins are limited to an explicitly documented immutable projection under the approved architecture.
3. **CQRS:** Classify each entry point as command or query. Commands load/lock roots and coordinate writes in the caller's transaction; they may read facts and replay snapshots needed for the command. Independent reads use immutable, owner-filtered projection ports and no aggregate hydration or save method. For list/detail reads, name the input-port view separately from the output-port model, the page hydration plan, expected query-count growth, and the consistency boundary for mutable state. Identify any cross-module transaction, lock order, version check, retry and idempotency requirement.
4. **Ports and adapters:** Map the inbound use-case port, handler, outbound ports, provider APIs, owning JDBC adapters, WebMVC facade/DTO mapper and response/error contract. The domain imports no framework or adapter type. Application code depends on contracts, never a JDBC implementation. The Web adapter uses the input port; MapStruct stays in adapters and does not create aggregates or authorize actors.
5. **Implementation route:** Order work by dependency: domain behavior; owner-module exported APIs and adapters; consuming command/query ports and handlers; consuming persistence and Web adapters. This is an implementation order after a valid RED gate, not permission to write production behavior before tests. Mark each file owner and any shared configuration or migration coordination.

The brief must show UC/BR/ARCH IDs and document revision/hash; domain behavior; a module/API/table-ownership map; command versus query and port/adapter map; expected response/errors; explicit file scope; unresolved decisions; and scenario-to-test mapping. Use the scenario template in `../docs-minimal/SolutionArchitecture/backend/4-automated-testing/4. Automated Testing.md` with stable IDs, Given/When/Then, persistence and forbidden effects, fixtures, cleanup and applicable concurrency behavior.

Before production implementation, write the scenario and automated test source and record a failing **behavioral** assertion. A compile, dependency, network, database-startup or zero-test failure is BLOCKED, not RED. For a behavior-preserving architecture refactor, record the failing structural assertion separately and keep existing behavior tests green; do not mislabel structural failure as behavioral RED. A missing provider API or unclear owner blocks that dependent slice until the contract and scope are resolved; never work around it with foreign SQL.
